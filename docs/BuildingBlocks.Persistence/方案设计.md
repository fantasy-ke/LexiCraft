# 持久化 BuildingBlocks 分层重构方案

- 更新时间：2026-08-14 17:46 +08:00
- 范围：`BuildingBlocks.EntityFrameworkCore`、`BuildingBlocks.EntityFrameworkCore.Postgres`、`BuildingBlocks.MongoDB`、公共持久化契约及直接业务调用方。

## 1. 目标

1. 让接口、基类、实现类、扩展类的物理目录与命名空间一致。
2. 让公共项目不直接依赖 EF Core/MongoDB 驱动，业务契约依赖抽象而不是提供程序。
3. 消除 Mongo 仓储的两套平行实现，统一事务、监控和重试边界。
4. 删除实现方无法满足的公共接口，避免 `NotSupportedException` 破坏里氏替换原则。
5. 保持现有业务行为与集合/数据库兼容，并通过定向测试和全量构建验证。

## 2. 类库边界

```text
BuildingBlocks
  └─ 领域标记/通用运行能力（无 EF/Mongo 驱动依赖）

BuildingBlocks.Persistence.Abstractions
  ├─ Repositories/IQueryRepository<TEntity>
  ├─ Repositories/IRepository<TEntity>
  └─ Transactions/IUnitOfWork
            ▲
            │ 实现
  ┌─────────┴───────────────────┐
  │                             │
BuildingBlocks.EntityFrameworkCore   BuildingBlocks.MongoDB
  ▲
  │ PostgreSQL 适配
BuildingBlocks.EntityFrameworkCore.Postgres
```

业务服务若声明或注入 `IRepository<>`、`IQueryRepository<>`、`IUnitOfWork`，应直接引用 `BuildingBlocks.Persistence.Abstractions`，不依赖传递引用。

## 3. 调整后的目录

### 3.1 公共契约

| 目录 | 类型 | 原位置 | 调整原因 |
|---|---|---|---|
| `Persistence.Abstractions/Repositories` | `IQueryRepository<>`、`IRepository<>` | `BuildingBlocks/Domain` | 仓储是持久化端口，不是领域实体/值对象。 |
| `Persistence.Abstractions/Transactions` | `IUnitOfWork` | `BuildingBlocks/Domain` | 工作单元属于持久化事务边界。 |

### 3.2 Entity Framework Core

| 目录 | 类型 |
|---|---|
| `Abstractions` | `IDataSeeder<TContext>` |
| `Repositories` | `QueryRepository<,>`、`Repository<,>` |
| `Transactions` | `UnitOfWork<TDbContext>` |
| `Interceptors` | `AuditableEntityInterceptor` |
| `Converters` | `StrongIdValueConverter<,>` |
| `Extensions` | DI、ModelBuilder、Queryable 扩展 |

删除只由实现类使用、向公共接口泄漏 `TDbContext` 的 `IRepository<TDbContext,TEntity>`；EF 实现直接实现提供程序无关的 `IRepository<TEntity>`。

### 3.3 PostgreSQL

| 目录 | 类型 |
|---|---|
| `Configuration` | `PostgresOptions` |
| `DesignTime` | `DbContextDesignFactoryBase<>` |
| `Migrations` | `MigrationSeedWorker<>`、`DefaultDataSeeder<>` |
| `Extensions` | PostgreSQL 注册、迁移注册扩展 |

委托 seeder 适配器不再隐藏在扩展类文件尾部，保证“一文件一个主要类型”和职责可发现性。

### 3.4 MongoDB

| 目录 | 类型 |
|---|---|
| `Abstractions` | `IMongoDbContext` |
| `Context` | `MongoDbContext` |
| `Entities` | `MongoEntity`、`MongoAggregateRoot` |
| `Repositories` | `MongoQueryRepository<>`、`MongoRepository<>` |
| `Resilience` | `IMongoResilienceService`、`MongoResilienceService` |
| `Performance` | 性能监控端口、实现和指标 |
| `Errors` | Mongo 异常映射 |
| `Serialization` | BSON 序列化提供程序 |
| `Configuration` | `MongoOptions` |
| `Extensions` | DI 与 ObjectId 扩展 |

`IMongoDbContext` 从通用 `BuildingBlocks` 移入 Mongo 项目后，根类库不再引用 `MongoDB.Driver`；根类库也移除了没有源码用途的 EF Core 包。

## 4. 设计模式与实现取舍

### 4.1 依赖倒置

业务契约面向 `Persistence.Abstractions`，EF/Mongo 项目作为适配器实现端口。提供程序包只停留在对应基础设施类库，不向通用领域项目扩散。

### 4.2 Repository + Unit of Work

- EF：仓储负责聚合访问，`IUnitOfWork` 负责 ChangeTracker 保存、事务和执行策略。
- Mongo：写操作即时落库；仓储仍提供统一命令接口，但 `SaveChangesAsync()` 仅为兼容旧公共契约并返回 `0`。

### 4.3 Template Method（Mongo 单一执行管线）

`MongoQueryRepository<TEntity>` 集中提供：

1. 性能计时；
2. 活动 session 发现；
3. 非事务读取重试；
4. 事务内绕过单语句重试；
5. session/非 session 的驱动重载选择。

`MongoRepository<TEntity>` 只增加写操作。业务自定义仓储通过受保护的 `FindAsync` / `FindPagedAsync` 扩展，不再选择 `MongoRepository` 与 `ResilientMongoRepository` 两套基类。

### 4.4 Composition Root

各项目的 `Extensions` 目录只负责注册与组装：

- EF 只扫描显式程序集注册仓储；
- PostgreSQL 组装 Npgsql、审计拦截器、工作单元和迁移；
- Mongo 组装 Client、Database、Context、性能监控和 Mongo 专属弹性服务。

`IMongoResilienceService` 避免 Mongo 注册覆盖同一容器中其他 `IResilienceService` 实现。

## 5. 已修复的正确性问题

1. 公共 `Select<TTemp>()` 和 `QueryNoTracking<T>()` 在 Mongo 中只能抛异常，已删除；调用方改用当前实体类型的 `QueryNoTracking()`。
2. Mongo 普通仓储支持事务但没有重试/监控，Resilient 仓储有重试/监控却绕过 Context session，现已合并。
3. 事务中的读取统一绑定当前 session；同一 session 的分页 count/list 串行执行。
4. 事务中的单条读操作不做局部重试，避免把事务的一部分重复执行。
5. Mongo 写操作不做应用层盲目重试，降低超时后重复写入的风险。
6. 根 `BuildingBlocks` 不再承担 Mongo Context 接口和数据库驱动依赖。
7. `IServiceCollection` 扩展移除了无法合理执行的 `Action<IHostApplicationBuilder>` 参数。
8. Files 服务修正 `Extentions` 拼写与 `With...` 注册命名，改为 `FilesStorageExtensions.AddLexiCraftDbAccess`。
9. Practice 的 `AnswerRecord` / `PracticeTaskItem` 实际内嵌在 `PracticeTask` 聚合文档中，原独立集合、只读仓储和索引没有写入路径，会形成永久空集合与错误查询入口；已按聚合边界删除这些独立持久化入口。同时修复 Context 以单数 `practice_task` 建索引、仓储却读写复数 `practice_tasks` 的命名分裂，双方统一引用 `PracticeTasksCollectionName`。`MistakeItem` 领域模型暂时保留，但在出现明确写入/查询用例前不注册集合仓储。

## 6. 性能处理

- Mongo `First/Any` 限制 1 条、`Single` 限制 2 条。
- 非事务分页并行 count/list，事务分页按 session 约束串行。
- 批量插入只枚举一次；空批次不访问服务器。
- 读取重试仅覆盖明确瞬态异常，避免认证、序列化和参数错误产生无效退避。
- 写入依赖驱动 retryable writes，不叠加应用层重试。
- 性能监控集中在统一仓储管线，避免业务仓储重复实现计时。
- 仓储注册只扫描显式传入的程序集，避免遍历所有依赖程序集。
- 分页 skip 使用 checked 运算，提前拒绝溢出参数。
- Practice 索引按实际查询改为 `(UserId, Status, FinishedAt)`、`(UserId, TaskType)`、`(UserId, SourceType)`，不再为从未写入的独立子文档集合创建索引。

## 7. 保留风险与后续建议

### P1：`IQueryable` 仍是提供程序逃生口

`Query()` / `QueryNoTracking()` 会把表达式翻译差异暴露给业务层，也绕过 Mongo 仓储的监控/重试执行函数。当前因已有复杂查询保留；若后续要求严格跨数据库替换，应引入显式查询对象或 Specification，而不是继续扩充通用仓储方法。

### P1：真实数据库集成和负载验证

当前验证覆盖单元/注册测试和全量编译，不等同于 PostgreSQL/MongoDB 容器集成测试。上线前应验证事务提交未知结果、断网重连、索引命中、分页大数据量和连接池压力。

### P2：`SaveChangesAsync()` 的跨提供程序语义不同

EF 延迟提交，Mongo 即时提交。为兼容已有 Identity/Vocabulary 调用暂未删除。后续可让 EF 命令统一注入 `IUnitOfWork`，再从仓储接口移除该方法。

### P2：`BuildingBlocks.Domain.Internal` 命名不准确

其中的 `AggregateRoot`、`IEntity`、`StrongId` 等是公开领域原语，并非 internal 实现。建议单独任务迁移到 `BuildingBlocks.Domain.Primitives`（或 `BuildingBlocks.Domain`），因为该改动会影响 MassTransit、序列化器和全部领域模型，不与本次持久化重构混合。

### P2：Mongo 集合命名契约

默认仓储仍使用实体类型名作为集合名；自定义仓储应显式传集合名。若要统一 snake_case/plural 规则，应先盘点线上集合并提供迁移，不可直接修改默认规则。

### P2：Practice 历史冗余索引清理

代码不再创建 `answer_records`、`mistake_items`、`practice_task_item` 的无效索引，并改为创建与实际查询匹配的命名复合索引；MongoDB 不会因代码删除自动移除线上旧索引。部署前应先通过 `$indexStats` / `explain()` 核对使用情况，再以独立运维步骤删除确认无用的历史索引。
