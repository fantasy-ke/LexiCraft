# 持久化 BuildingBlocks 代码审查

- 审查日期：2026-08-13
- 范围：`BuildingBlocks.EntityFrameworkCore`、`BuildingBlocks.EntityFrameworkCore.Postgres`、`BuildingBlocks.MongoDB` 及受公共接口影响的直接调用链。
- 目标：修复正确性遗漏，收敛 DI/迁移/重试边界，并降低查询、反射和监控开销。

## 已修复问题

### P0：EF 软删除逻辑会丢失删除状态

原实现对 `Deleted` 实体调用 `Reload()`，但没有稳定地把删除转换为更新，容易丢失待写入的删除字段，甚至继续执行物理删除。现在只把 `IsDeleted` 和删除审计属性标记为已修改，既保留数据库行，也避免脱离跟踪的仅主键实体把其他列覆盖为默认值；SQLite 回归测试覆盖了这两种场景。

### P0：注册 DbContext 时构造临时 ServiceProvider

原 PostgreSQL 注册代码在 `AddDbContext` 中调用 `BuildServiceProvider()`，会创建第二套单例/作用域图，使 `IUserContext`、日志和其他 scoped 依赖来源错误。现在审计拦截器按 scoped 注册，并从当前 DbContext scope 解析。

### P1：迁移失败被吞掉

原迁移 worker 只记录异常，应用可能在 schema 未更新或 seed 未完成时继续启动。现在迁移与 seed 使用异步 scope、传播 `CancellationToken`，失败后重新抛出，测试覆盖 seed 异常向启动方传播。

### P1：Mongo 自定义配置节未被完整使用

原注册路径可能注册一个配置节，却从另一个固定节读取配置。现在统一按调用方传入的 section 绑定，并校验连接字符串、数据库名和连接池边界。

### P1：Mongo 异常映射可能被默认注册遮蔽

原注册使用 `TryAddSingleton<IProblemCodeMapper, MongoDbProblemCodeMapper>`；如果验证模块先注册默认 mapper，Mongo mapper 会被跳过，连接异常等错误只能返回通用 500。现在用 `Replace` 让 Mongo mapper 成为主映射器，并由它继续委托 `DefaultProblemCodeMapper` 处理非 Mongo 异常；重复注册也不会累计多个主映射器。

### P1：Mongo 全局映射重复注册

原逻辑每次注册 Context 都再次注册 BSON convention/serializer，多 Host 和测试进程可能抛出重复注册异常。现在通过线程安全的 `Lazy` 只初始化一次，同时保留全局 camelCase 和字符串枚举对嵌套文档的兼容。

### P1：Mongo 事务内读取绕过当前 session

原通用查询仓储只在写操作中使用 `MongoDbContext.Session`，事务内先写后读可能看不到同一事务中的变更。现在所有 Find、Count 和 LINQ 查询都绑定活动 session；分页在非事务场景并行，在事务 session 内串行，避免驱动不支持的同 session 并发操作。提交或回滚失败时不提前释放 session，调用方仍可继续完成事务收尾。

### P1：取消令牌在仓储、事务和业务调用链中丢失

EF/Mongo 仓储、工作单元、迁移、seed 及 Identity/Vocabulary/Practice/Files 的直接调用统一向底层传递 `CancellationToken`。业务请求取消时不再继续占用数据库连接执行无用 I/O。

### P2：查询和监控存在额外开销

- Mongo `Any`/`First` 限制最多读取 1 条，`Single` 最多读取 2 条。
- Mongo 非事务分页的 count/list 并发执行；事务分页绑定同一 session 串行执行，并移除同步 `CountDocuments`。
- 批量写入只枚举输入一次，空集合不再调用 `InsertManyAsync`。
- 强类型 ID 构造从每次反射改为每个泛型类型编译一次委托。
- 性能监控关闭时零记录，在并发记录下将内存队列精确限制为 10,000 条，读取时仅对快照做时间窗口过滤，避免并发清理误删新指标。
- 重试只处理明确 transient 的 Mongo 异常，避免认证/序列化/参数错误的无意义退避。
- Identity 初始化权限由逐条存在性查询改为一次集合查询，减少启动期数据库往返。

## 验证覆盖

新增 `BuildingBlocks.Persistence.Tests`，覆盖：

- EF 审计、UTC 时间、软删除字段隔离、分页参数及分页扩展取消传播；
- 强类型 ID 转换；
- PostgreSQL 连接字符串 fallback、缺失配置、迁移失败传播；
- Mongo 自定义配置节、异常映射替换与默认 fallback、重复注册、嵌套文档约定、数据库名、连接池校验、显式集合名、空批量写入和写管线 session/重试边界；
- Mongo 监控开关、指标上限和时间窗口校验；
- Mongo transient/non-transient 重试和预取消行为。

## 保留风险与后续建议

1. `IRepository.DeleteAsync(predicate)` 在 EF 中使用 `ExecuteDeleteAsync`，按设计绕过拦截器并物理删除；本次为兼容未改语义，README 已明确警告。
2. Mongo 写操作发生超时后重试仍可能重复产生业务效果；需要由具体命令通过唯一索引、幂等键或事务补齐，基础组件无法安全猜测。
3. 统一后的 `MongoQueryRepository<TEntity>` / `MongoRepository<TEntity>` 默认都使用实体类型名作为集合名；Practice 通过具体仓储显式绑定 `practice_tasks`。若未来使用自动仓储或调整 plural/snake_case 规则，必须先盘点线上集合并提供数据迁移，不能直接修改默认规则。
4. PostgreSQL 仍保留 legacy timestamp 开关以兼容历史数据；移除前需做数据库列类型和数据迁移审计。
5. 本次完成单元测试、项目构建和解决方案构建，不等同于真实 PostgreSQL/MongoDB 集成测试或负载基准。生产性能结论仍需结合真实索引、数据量、拓扑和网络延迟验证。

## 2026-08-14 17:46 +08:00：目录、类库边界与设计模式复审

### 审查结论

本轮未发现阻断构建的遗漏；发现并修复了 5 类结构性风险：

1. **P1—依赖方向错误**：通用 `BuildingBlocks` 因 `IMongoDbContext` 直接依赖 Mongo 驱动，且残留无源码用途的 EF Core 包。已把 Mongo Context 端口移入 `BuildingBlocks.MongoDB`，公共仓储端口移入新的 `BuildingBlocks.Persistence.Abstractions`。
2. **P1—里氏替换违规**：公共仓储包含 Mongo 无法实现的跨实体泛型 API，只能运行时抛 `NotSupportedException`。已删除该接口能力和无调用的 `Select<TTemp>()`，业务查询改用当前实体类型 API。
3. **P1—Mongo 平行继承树语义分裂**：普通仓储支持 session，Resilient 仓储支持监控/重试但绕过 session。已合并为单一 Template Method 管线，事务读写与性能监控不再二选一。
4. **P2—服务注册冲突**：Mongo 直接注册全局 `IResilienceService`，可能覆盖同进程其他实现。已新增 `IMongoResilienceService` 作为提供程序专属端口。
5. **P1—Practice 聚合与集合模型冲突**：答案和练习项只随 `PracticeTask` 聚合文档写入，但原代码同时暴露独立集合、只读仓储和索引；这些入口没有写入路径，查询会长期返回空数据。已删除独立持久化入口，并保留聚合根作为唯一写入边界。另将 Context 与仓储统一到共享的 `practice_tasks` 集合名常量，避免索引建到单数空集合。

### 文件与命名审查

- EF 的接口、仓储、事务、扩展已分入 `Abstractions`、`Repositories`、`Transactions`、`Extensions`。
- PostgreSQL 的配置、设计时工厂、迁移实现和扩展已分入对应目录；`DefaultDataSeeder` 从扩展文件中拆出。
- Mongo 的 Context、实体基类、仓储、异常、弹性、性能、序列化和配置目录职责明确。
- Files 服务的 `Extentions` 拼写和注册方法命名已修正。
- 暂不移动 `BuildingBlocks.Domain.Internal` 中的公开领域原语；该变更影响面跨越整个解决方案，已列为独立 P2 任务。

### 性能审查

- 保留非事务分页 count/list 并行；事务 session 内严格串行。
- 事务操作不做单语句局部重试；写入不做应用层盲重试。
- 统一仓储管线减少重复查询实现和重复计时代码。
- 空批量写入零 I/O；扫描范围只覆盖显式程序集。
- Practice 停止为无写入路径的集合创建索引；提交后复审进一步确认三个复合查询没有调用方，因此也删除对应的推测性索引。线上历史集合和索引仍需在 `$indexStats` / `explain()` 验证后单独清理。

## 2026-08-14：提交后遗漏复审

### 新发现并已修复

1. **P1—无调用查询与推测性索引**：`IPracticeTaskRepository` 暴露的按用户/状态/类型/来源查询，以及实现中额外的活动任务列表查询，在整个解决方案没有调用方；Practice 当前真实持久化调用只有插入、按 `_id` 获取和按 `_id` 替换。原三组复合索引会增加索引空间、每次写入维护成本和启动 I/O，却没有当前收益。现已删除这些方法、业务专用空接口和索引 seeder，仅保留具体仓储对稳定集合名 `practice_tasks` 的绑定；处理器依赖公共 `IRepository<PracticeTask>` 端口。
2. **P1—scoped seeder 逃逸生命周期**：原 `UseInfrastructure()` 在临时 scope 中解析 `PracticeDbDataSeeder`，随后把该 scoped 实例捕获到未托管的 `Task.Run`；方法返回后 scope 立即释放，后台任务可能使用已释放的 Context，异常也不进入 Host 启停生命周期。由于该 seeder 只服务于上述无调用查询索引，现直接删除注册和 fire-and-forget 启动逻辑，而不是再增加一层 HostedService。
3. **P2—集合名与写管线缺少直接回归测试**：新增测试确认自定义集合名同时作用于仓储监控名称和 Driver collection，并确认事务内写管线绑定当前 session 且不经过应用层 resilience。

### 调整后的结构取舍

- `PracticeTaskRepository` 是有实际职责的 Mongo 适配器：固定业务集合名；不再承载没有用例的查询方法。
- 应用处理器依赖 provider-neutral 的 `IRepository<PracticeTask>`，避免为零扩展方法创建服务专属接口。
- 当前仅依赖 MongoDB 内置 `_id` 索引。新查询和新索引必须由实际端点、过滤条件、排序、分页及 `explain()` 结果共同驱动。
- 详细的并发一致性、Outbox、真实数据库测试、在线索引迁移和公共接口收敛任务见 [`后续任务.md`](./后续任务.md)。
