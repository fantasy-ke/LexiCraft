# 持久化重构后续独立任务

- 制定日期：2026-08-14
- 基线提交：`bf041b6 refactor: 调整持久化组件分层`
- 适用范围：`BuildingBlocks.Persistence.Abstractions`、EF Core/PostgreSQL/MongoDB 适配器，以及 Identity、Vocabulary、Practice、Files 的直接持久化调用方。

## 1. 为什么必须拆分

本次提交后复审已经修复能够由静态调用链直接证明的问题：Practice 无调用查询、推测性索引、scoped seeder 逃逸生命周期，以及集合名/写管线测试遗漏。以下项目会改变业务一致性、公开接口、线上数据或部署方式，不应继续混入同一个重构提交。

拆分原则：

1. 先确定业务契约，再设计仓储和索引，不为假设需求预建能力。
2. 先补可失败的回归/集成测试，再改变事务、并发或重试语义。
3. 线上集合、索引和数据迁移必须有盘点、回滚和观测，不由应用启动代码静默执行。
4. 每个任务只处理一个主要风险，独立提交、独立验收。

## 3. 任务明细

### T1：Practice 聚合并发控制与事件一致性

**代码事实**

- `SubmitAnswerHandler` 与 `CompletePracticeHandler` 都先按 `_id` 读取完整 `PracticeTask`，再通过 `ReplaceOne` 替换整个文档。
- 更新过滤条件当前只有 `_id`，并发提交答案或“提交答案/完成练习”交错时，后写者可能覆盖先写者。
- 完成处理先更新 Mongo，再发布 `PracticeCompletedIntegrationEvent` 和错误单词事件；若发布失败，重试请求可能因任务已经完成而提前返回，造成事件永久缺失。

**实施范围**

1. 为聚合增加明确的并发令牌，例如 `Version`，更新过滤使用 `_id + Version` 并原子递增版本；并发冲突映射为可识别的 409，而不是无条件覆盖。
2. 明确同一题重复提交的幂等键与返回结果；禁止仅依赖应用层自动重试。
3. 使用现有消息基础设施选定一种 Outbox 实现，保证聚合状态和待发布事件在同一 Mongo 事务中提交；记录事件版本、幂等键、重试与重复消费规则。
4. 确认部署 Mongo 拓扑支持事务（副本集/分片集群），不支持时必须选择可证明的替代一致性方案。

**不在范围**

- 不同时引入第二套事件总线。
- 不在没有并发契约时改成大范围通用 Repository API。

**验收标准**

- 两个并发答案更新不会静默丢失；一个成功，另一个得到确定的冲突/幂等结果。
- Mongo 提交成功但消息发送失败后，Outbox 可恢复发布；重复投递不会重复产生业务副作用。
- 覆盖“提交答案与完成同时发生”“完成请求重试”“消息代理短暂不可用”测试。

### T2：真实 PostgreSQL/MongoDB 集成与故障测试

**目标**

建立可重复的 Testcontainers 测试基座，验证当前单元测试无法覆盖的驱动、事务和数据库行为。

**实施范围**

1. PostgreSQL：迁移成功/失败、seed 失败传播、审计字段、软删除、`ExecuteDeleteAsync` 物理删除语义、取消令牌。
2. MongoDB：显式 `practice_tasks` 集合、事务 session、提交未知结果、回滚、断线、超时、retryable writes 和连接池边界。
3. Mongo 事务测试使用副本集容器；普通 standalone 容器不能作为事务通过证明。
4. 把数据库镜像版本固定在与部署环境兼容的版本；CI 超时和日志保留规则明确。

**验收标准**

- 本地和 CI 均可一条命令执行；失败时保留容器日志和数据库错误。
- 至少覆盖一次真实迁移、一次真实 Mongo 事务和一次故障注入。
- 将“静态/单元通过”和“真实数据库通过”分开报告。

### T3：Practice 查询契约与在线索引迁移

**当前边界**

Practice 现有运行路径只有插入、按 `_id` 查询和按 `_id` 替换，MongoDB 内置 `_id` 索引足够；已经删除没有调用方的用户/状态/类型/来源查询及对应索引。

**实施前必须确认**

1. 是否需要“进行中任务”“历史任务”“按类型/来源筛选”等端点。
2. 分页方式、稳定排序字段、最大页大小和数据保留周期。
3. 是否要求“每个用户只能有一个进行中任务”；如果需要，必须定义并发创建冲突语义，再评估 partial unique index。

**实施范围**

1. 先实现端点契约和有界查询，再基于真实 filter/sort 设计索引。
2. 使用生产等量级样本执行 `explain('executionStats')`，记录扫描文档数、扫描索引键数和延迟。
3. 盘点 `practice_task`、`practice_tasks` 以及历史子文档集合；通过 `$indexStats` 确认旧索引使用情况。
4. 索引创建/删除使用独立部署步骤或受 Host 管理、失败可见的迁移，不使用 fire-and-forget `Task.Run`。
5. 为每个删除操作提供名称、环境、备份/重建命令和回滚窗口；应用代码不自动删除线上索引。

**验收标准**

- 每个新增索引都能对应到一个已上线查询和 `explain()` 证据。
- 查询有分页上限和稳定排序，不允许无界 `FindAsync` 返回全部历史任务。
- 迁移在预生产完成演练，具备回滚步骤和部署后监控。

### T4：用 Query Object/Specification 收敛 `IQueryable`

**代码事实**

提交后扫描仍有 18 个 `Query()` / `QueryNoTracking()` 调用，集中在 Identity 与 Vocabulary。它们把 EF 翻译能力暴露给应用层，也可能绕过仓储统一的监控/弹性执行边界。

**实施范围**

1. 按真实用例逐个建立 Query Object 或 Specification，返回 DTO/投影，不创建一个包含任意表达式的新“万能仓储”。
2. 优先处理搜索、词表、弱词和 OAuth/User 组合查询；为分页、排序和投影建立提供程序翻译测试。
3. 调用迁移完成后，再决定是否从公共接口删除 `Query()` / `QueryNoTracking()`。
4. 同步盘点无界 `GetListAsync()` / `FindAsync()` 调用，只有确实有数据上限的场景可以保留。

**验收标准**

- 目标调用方不再直接组合 provider-specific `IQueryable`。
- 生成 SQL/查询计划可验证，没有客户端求值和 N+1。
- 每次迁移保持响应 DTO、排序和分页契约不变。

### T5：拆分 `SaveChangesAsync` 与工作单元语义

**问题**

`IRepository<TEntity>.SaveChangesAsync()` 在 EF 表示提交 ChangeTracker，在 Mongo 返回 `0` 且写操作早已生效，同一接口具有不同语义。

**实施范围**

1. 盘点 Identity/Vocabulary/Files 的全部调用；EF 命令改为显式注入 `IUnitOfWork`。
2. 分阶段标记仓储 `SaveChangesAsync` 为 obsolete，迁移内部调用后再删除。
3. 明确事务执行器委托的取消令牌传递，避免内部闭包忽略 Host/request cancellation。
4. Mongo 事务重试只能重试完整事务单元，不能恢复单语句局部重试。

**验收标准**

- Repository 只负责聚合读写，提交职责由 EF Unit of Work 明确承担。
- Mongo 调用方不再误判 `SaveChangesAsync()` 返回值。
- 公共 API 删除有版本与兼容说明。

### T6：多持久化上下文 DI 契约

**问题**

当前 `IMongoClient`、`IMongoDatabase`、`IMongoDbContext` 和 `IUnitOfWork` 主要按单 Context Host 使用；同一进程注册多个数据库时，非 keyed 服务可能出现最后注册覆盖或解析歧义。

**实施范围**

1. 先增加“双 Mongo Context/双 EF Context”注册测试，证明当前行为。
2. 在 keyed services、强类型 context-only 注入和显式 fail-fast 单 Context 约束之间选择最简单方案。
3. 不为尚不存在的多数据库 Host 提前增加复杂工厂；如果决定只支持单 Context，应在第二次注册时明确失败。

**验收标准**

- 多 Context 行为由测试固定，不依赖 DI 注册顺序猜测。
- 每个仓储解析到正确的 client/database/context。

### T7：领域原语与审计用户端口移库

**问题**

- `BuildingBlocks.Domain.Internal` 中的 `AggregateRoot`、`IEntity`、`StrongId` 等是公开领域原语，目录/命名空间与可见性不符。
- EF 审计仅需要当前用户标识，却通过 `BuildingBlocks.Authorization` 间接带入更重的授权/缓存依赖。

**实施范围**

1. 把公开领域原语迁移到 `BuildingBlocks.Domain.Primitives` 或经评审确定的稳定命名空间。
2. 提取轻量 `IUserContext`/`ICurrentUser` 端口到低层抽象项目，由 Authorization 提供实现。
3. 评估 MassTransit、BSON/JSON 序列化、StrongId converter、所有领域模型和外部包消费者的兼容性。
4. 如组件已发布，提供 obsolete forwarding/shim 或主版本升级说明，而不是静默删除旧命名空间。

**验收标准**

- EF Core 不再为了审计用户依赖完整 Authorization/Caching 实现。
- 序列化格式、消息契约和数据库字段不变。
- 全解决方案及兼容性测试通过。

### T8：公共 API 兼容、可观测性与性能基准

**实施范围**

1. 对 `bf041b6` 删除/迁移的命名空间和类型生成公开 API diff；确认这些 BuildingBlocks 是否被仓库外项目或 NuGet 包消费。
2. 如果存在外部消费者，按 SemVer 决定兼容 shim、迁移窗口或主版本发布。
3. 评估 `MongoResilienceService` 生命周期和策略构造成本；先用基准证明，再决定是否改为 singleton/缓存策略，避免仅凭直觉重构。
4. 将关键数据库耗时、重试次数、连接池等待、事务冲突和 Outbox 积压接入 OpenTelemetry；进程内 10,000 条队列只保留为诊断辅助。
5. 使用 BenchmarkDotNet 或受控负载测试对比分页、批量写入、索引前后和高并发 session，记录数据量、拓扑、硬件及网络条件。

**验收标准**

- 兼容性结论有 API diff 和消费者清单。
- 性能结论包含基线、方法、数据和可重复结果，不以“构建通过”代替吞吐验证。
- 指标有明确名称、单位、标签基数和告警阈值。

## 4. 每个独立任务的统一交付模板

每项任务至少包含：

1. 代码事实和受影响调用链。
2. 范围、非范围、兼容性与回滚方案。
3. 先失败后通过的回归测试，或无法自动化时的可重复验证步骤。
4. 定向项目构建、`dotnet build src/LexiCraft.slnx --no-restore`、`git diff --check`。
5. 真实数据库/压力验证与单元/静态验证分开记录。
6. 只提交该任务文件的 Conventional Commit，不混入本地数据库文件或用户设置。
