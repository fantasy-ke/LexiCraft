# LexiCraft 架构优化与前后端联调方案

## 2026-08-07 18:41

## 技术方案概述

本方案针对 LexiCraft 当前的多服务后端、YARP 网关、AgileConfig 配置和 Vue 前端并行演进问题，目标是先建立一条可验证的前后端联调链路，再逐步统一 API 契约、测试门禁、配置治理和代码维护边界。

方案遵循现有技术栈，不新增替代性网关、数据库或前端状态框架。第一阶段只解决“请求能否到达正确服务、响应能否被稳定解析、认证能否持续工作”三个问题；路由来源、字段格式和业务规则未确认前，不直接大范围迁移旧 API。

本轮 P0 优化不以配置清理作为前置条件。现有本地局域网地址（包括 `172.31.21.1`）以及当前使用的 AgileConfig `Secret`、连接密码等配置继续保留，不删除、不替换、不迁移；新增代码只读取现有配置，不复制新的凭据。密钥轮换和配置外置属于后续治理事项，不作为本轮联调完成的阻断条件。

| 层次 | 当前实现 | 证据位置 |
| --- | --- | --- |

| Identity | JWT、登录注册、OAuth、用户资料、权限 | `src/microservices/Identity/` |
| Vocabulary | 词库、单词查询、导入、用户单词状态 | `src/microservices/Vocabulary/` |
| Practice | 任务、答案评估、完成任务 | `src/microservices/Practice/` |

后端代码定义的模块前缀是：

- `api/v{version:apiVersion}/identity`
- `api/v{version:apiVersion}/vocabulary`
- `api/v{version:apiVersion}/practice`

仓库中的网关基础 `appsettings.json` 只保留空的 `ReverseProxy` 节点，但 `appsettings.Development.json` 和 `appsettings.Docker.json` 已提供环境级路由。AgileConfig 或运行环境仍可能覆盖这些配置，因此 P0 以“环境配置来源 + 路由快照 + 实际请求”三项证据确认最终生效值。

当前代码中已确认的路由转换如下，`/api` 是转发到后端服务的内部前缀，不是前端公共地址的一部分：

| 公共入口 | 后端目标路径 | 目标服务 |
| --- | --- | --- |
| `/files/{**catch-all}` | `/{**catch-all}` | `files-grpc` |
| `/identity/{version:regex(^v\d+)}/{**catch-all}` | `/api/{version}/identity/{**catch-all}` | `identity-api` |
| `/vocabulary/{version:regex(^v\d+)}/{**catch-all}` | `/api/{version}/vocabulary/{**catch-all}` | `vocabulary-api` |
| `/practice/{version:regex(^v\d+)}/{**catch-all}` | `/api/{version}/practice/{**catch-all}` | `practice-api` |

## 优化目标与优先级

### P0：建立可验证联调链路（本轮执行范围）

1. **统一网关公共基址**
   - 前端只读取 `VITE_API_BASE_URL`，所有服务路径由 `API_ROUTES` 从同一个网关基址派生。
   - 浏览器运行时默认使用同源 `/`；本地网关目标仅由 Vite 的 `VITE_DEV_GATEWAY_TARGET` 代理配置提供，避免运行时代码固化 `localhost`。
   - 禁止新增 `localhost:5001`、`localhost:5002` 等服务直连兜底；旧业务 API 的路径迁移留在 P1，避免本轮扩大范围。

2. **固定并验证 YARP 路由契约**
   - 以环境实际加载的 `ReverseProxy` 为准，输出只包含 route、cluster、destination、transform 的脱敏快照，不把 Secret 或密码写入快照。
   - 固定四条公共入口及路径转换：`identity`、`vocabulary`、`practice` 使用 `/v1` URL 版本段，`files` 保持无版本入口。
   - 至少验证验证码、登录、用户资料和一个文件内容请求分别命中预期服务；404、权限失败和服务不可达必须保留真实 HTTP 状态。

3. **统一认证和响应边界**
   - 认证请求统一使用 `Authorization: Bearer <token>`；登录、注册、刷新、OAuth、密码找回等匿名端点不携带失效 Token，也不触发刷新循环。
   - 后端当前线上的 `ResultDto`/`TokenResponse` 采用 PascalCase（`Status`、`Data`、`StatusCode`、`Token`、`RefreshToken`）；前端在 HTTP 边界一次性归一化，业务层不再分散兼容判断。
   - 刷新令牌沿用后端当前轮换语义；正常请求只在令牌临近过期时刷新，收到 401 时强制刷新一次，并发请求共享同一个刷新 Promise，失败后清理会话。
   - 后端当前未返回 `expiresIn`，客户端优先读取 JWT 的 `exp`；不能把 `expiresIn` 当作本轮必须新增的后端字段。

4. **保留现有联调配置，不把清理工作混入 P0**
   - `172.31.21.1` 作为本地局域网地址保留；现有 AgileConfig `Secret`、数据库/缓存/对象存储密码等也按当前部署方式保留。
   - 本轮不删除、不轮换、不替换这些值，也不因为它们仍在现有配置中而阻塞登录链路验证；后续如需安全治理，单独建立迁移和轮换任务。

5. **完成最小主链路冒烟**
   - 网关健康检查 → 验证码 → 注册/登录 → 获取用户资料 → 令牌过期刷新 → 登出。
   - 每一步记录请求公共地址、实际路由、HTTP 状态、响应包络和追踪 ID；没有真实运行环境时只能标记为“静态/构建验证”，不能写成运行时通过。

### P0 完成定义

- 前端认证请求只经由一个可配置网关基址，仓库中不存在认证客户端的服务直连 fallback。
- `Status`/`Data`/`Token` 等实际响应能够被前端稳定解析为内部统一的 `ResultDto` 和 Token 结构。
- 同一失效令牌触发的并发 401 只产生一次刷新请求，原请求最多重放一次。
- 路由快照与实际请求结果能够证明 Identity、Vocabulary、Practice、Files 的路径转换没有漂移。
- 现有局域网地址、Secret 和密码配置保持不变；它们不是本轮 P0 的删除对象。

## 前后端统一契约设计

### 1. 公共地址

前端只配置一个网关公共基址：`VITE_API_BASE_URL`。代码中的服务域只保存相对路径，不保存 Identity、Vocabulary、Practice 或 Files 的内部端口。

- 默认本地开发基址为 `http://localhost:5000`，仅作为没有注入环境变量时的开发 fallback。
- 使用局域网联调时，直接把现有的 `172.31.21.1` 和端口注入 `VITE_API_BASE_URL`，不替换、不删除，也不把该地址当成公网地址。
- 认证请求形如 `${VITE_API_BASE_URL}/identity/v1/login`；文件请求形如 `${VITE_API_BASE_URL}/files/content`。
- 后端目标路径中的 `/api/v1/...` 由 YARP transform 生成，前端不重复拼接 `/api`。
- `appsettings.Development.json` 与 `appsettings.Docker.json` 的路由是当前代码事实；AgileConfig/运行环境覆盖后的最终结果仍需在目标环境实测确认。

### 2. 响应包络

后端 `ConfigureJson()` 当前关闭了默认命名策略，线上 JSON 字段以 PascalCase 为准；`ResultEndPointFilter` 会把普通端点结果包装为 `ResultDto`，文件流例外。典型成功响应为：

```json
{
  "Status": true,
  "Message": "",
  "StatusCode": 200,
  "Data": {}
}
```

前端在 `apiClient` 边界统一归一化为内部结构：

```ts
{
  status: true,
  message: '',
  statusCode: 200,
  data: {}
}
```

失败响应必须保留以下信息：

- HTTP 状态：400、401、403、404、409、429、5xx。
- 包络中的 `Status`/`Message`/`StatusCode`/`Data`（若服务返回包络）。
- `Retry-After`、追踪 ID 或其他诊断头（若网关/服务提供）。
- 文件流按 `Content-Type` 处理，不强制包装成 JSON。

前端不得把 HTTP 错误静默转换成成功结果，也不得因为字段大小写差异重新实现一套业务错误判断。

### 3. 认证契约

后端当前 `TokenResponse` 的真实字段为 `Token` 和 `RefreshToken`，不包含 `expiresIn`；前端 HTTP 边界将其归一化为业务层使用的 `token` 和 `refreshToken`，不再依赖大小写猜测。

- 请求头统一为：`Authorization: Bearer <token>`。
- 登录、注册、刷新和 OAuth 回调的返回字段使用归一化后的 Token 结构；后端不因本轮前端适配被迫新增 `accessToken` 或 `expiresIn`。
- 令牌有效期优先从 JWT `exp` 计算；本地状态的兜底时间不作为服务端契约。
- 后端刷新实现会删除旧刷新令牌并生成新的刷新令牌，本轮沿用该轮换语义。
- 普通请求只在访问令牌临近过期时刷新；收到 401 时强制刷新一次，并发请求共享同一个刷新 Promise。
- 登录/注册/刷新/OAuth/密码找回等匿名端点不得携带失效令牌导致刷新循环。
- 注册密码校验仍以服务端规则为准；现有密码配置和值保留，本轮只验证前后端规则差异，不删除密码字段或密码配置。

### 4. 权限契约

后端端点使用权限声明；后端需提供权限码清单和端点映射。前端统一处理：

- 401：尝试一次刷新，失败后清理会话并跳转登录。
- 403：显示无权限状态，不误判为未登录。
- 429：显示限流提示并遵守 `Retry-After`（若提供）。
- 业务操作按钮根据权限状态隐藏、禁用或在服务端拒绝后给出明确反馈。

## 配置与部署设计

1. 保留当前各环境的配置加载方式；P0 只验证配置来源和最终生效值，不为了“安全清理”删除已有联调配置。

3. YARP 路由建立只包含 route、cluster、destination、transform 的脱敏快照；快照不记录 Secret、密码、连接字符串或令牌。

5. 生产 CORS 只允许明确的前端域名；同步配置 OAuth 回调、文件域名和 CSP 资源来源。该项属于运行环境验收，不要求本轮删除本地配置。

## 测试与验收设计

### P0 验收

- Given 网关使用当前环境配置启动，When 访问健康检查和路由探针，Then 能证明公共入口与目标服务均可达，且路由转换与快照一致。
- Given `VITE_API_BASE_URL` 指向本机或 `172.31.21.1` 的网关地址，When 请求验证码，Then 前端得到统一的 `captchaData` 和 `captchaKey`，请求不直连 Identity 服务端口。
- Given 合法注册或登录数据，When 调用 `/identity/v1/register` 或 `/identity/v1/login`，Then `Status`/`Data`/`Token`/`RefreshToken` 能被前端归一化，且能建立会话。
- Given 有效访问令牌，When 请求用户资料，Then 使用 `Authorization: Bearer` 经网关路由到 Identity，并返回统一包络。
- Given 访问令牌过期或服务返回 401 且刷新令牌有效，When 多个请求同时失败，Then 只发生一次刷新，刷新后的原请求最多重放一次。
- Given 路由、权限、参数、限流或服务错误，When 请求失败，Then 前端能区分 400/401/403/404/409/429/5xx，不把失败包装成成功。
- Given 当前环境仍使用 `172.31.21.1`、Secret 或密码，When 完成 P0 验收，Then 这些配置值保持原样，且未因本轮优化被删除或替换。
