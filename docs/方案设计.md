# LexiCraft 架构优化与前后端联调方案

## 2026-08-07 18:21

## 技术方案概述

本方案针对 LexiCraft 当前的多服务后端、YARP 网关、AgileConfig 配置和 Vue 前端并行演进问题，目标是先建立一条可验证的前后端联调链路，再逐步统一 API 契约、测试门禁、配置治理和代码维护边界。

方案遵循现有技术栈，不新增替代性网关、数据库或前端状态框架。第一阶段只解决“请求能否到达正确服务、响应能否被稳定解析、认证能否持续工作”三个问题；路由来源、字段格式和业务规则未确认前，不直接大范围迁移旧 API。

## 当前架构事实

| 层次 | 当前实现 | 证据位置 |
| --- | --- | --- |
| 前端 | Vue 3、TypeScript、Vite、Pinia、Vue Router、Axios | `src/UIs/lexicraft-vue-frontend/package.json` |
| 编排 | .NET Aspire Host 注册网关、Identity、Vocabulary、Practice、Files | `src/LexiCraft.Aspire.Host/AppHost.cs` |
| 网关 | YARP、CORS、限流、安全响应头、健康端点 | `src/ApiGateway/LexiCraft.ApiGateway/Program.cs` |
| 服务默认能力 | AgileConfig、服务发现、HttpClient resilience、健康检查、OpenTelemetry | `src/LexiCraft.Aspire.ServiceDefaults/Extensions.cs` |
| Identity | JWT、登录注册、OAuth、用户资料、权限 | `src/microservices/Identity/` |
| Vocabulary | 词库、单词查询、导入、用户单词状态 | `src/microservices/Vocabulary/` |
| Practice | 任务、答案评估、完成任务 | `src/microservices/Practice/` |
| Files | gRPC、内容读取、静态文件、OSS | `src/microservices/Files/` |
| 统一响应 | `ResultDto`，文件流端点为例外 | `src/BuildingBlocks/BuildingBlocks/Shared/ResultDto.cs`、`Filters/ResultEndPointFilter.cs` |

后端代码定义的模块前缀是：

- `api/v{version:apiVersion}/identity`
- `api/v{version:apiVersion}/vocabulary`
- `api/v{version:apiVersion}/practice`

仓库中的网关 `appsettings.json` 只保留空的 `ReverseProxy` 节点，实际路由是否由 AgileConfig 或运行环境补充必须通过运行配置或 OpenAPI 验证。

## 优化目标与优先级

### P0：建立可验证联调链路

1. 明确各环境唯一的网关公共基址。
2. 固定网关路径前缀和 YARP 路径转换规则。
3. 统一认证请求头、令牌字段、刷新行为和 `ResultDto` 错误包络。
4. 迁移仓库中明文配置到环境变量、用户机密或部署密钥管理。
5. 完成登录主链路和网关路由冒烟验证。

### P1：补齐业务契约和工程门禁

1. 建立 `identity`、`vocabulary`、`practice`、`files` 四个前端 API 域模块。
2. 用 OpenAPI 或共享契约生成/校验 TypeScript DTO。
3. 增加网关、Identity、Vocabulary、Practice、Files 的最小契约测试。
4. 让 Vitest 测试脚本真实可执行，并将类型检查/构建纳入 CI。
5. 统一 `src/LexiCraft.slnx` 与根 `LexiCraft.sln` 的项目职责。

### P2：降低长期维护成本

1. 拆分已超过 800 行的后端和前端活跃文件。
2. 明确生产健康探针、CORS、CSP、限流和 OpenTelemetry 导出策略。
3. 补充事件版本、幂等、重试、补偿和跨服务一致性文档。
4. 清理 README、Docker 部署文档与实际项目清单之间的漂移。

## 前后端统一契约设计

### 1. 公共地址

前端只配置一个网关公共基址，例如通过 `VITE_API_BASE_URL` 提供；服务域只保存相对路径，不保存服务内部端口。

待后端确认：

- 网关是否以 `/api` 作为统一前缀。
- Identity、Vocabulary、Practice、Files 是否分别使用 `/identity`、`/vocabulary`、`/practice`、`/files`。
- 版本号由 URL 段、`api-version` 请求头还是查询参数传递。建议公共客户端统一使用 URL 版本段。
- 开发、测试、生产的公共基址和 HTTPS 要求。

### 2. 响应包络

以服务端 `ResultDto` 为候选唯一包络：

```json
{
  "status": true,
  "message": "",
  "statusCode": 200,
  "data": {},
  "extensions": {}
}
```

需要通过实际 JSON 响应确认字段大小写和失败响应结构。确认后：

- 成功响应由 API 层返回 `data` 或完整包络，不能在不同客户端混用。
- 400、401、403、404、409、429、5xx 和网络错误统一映射为前端错误类型。
- 不把 HTTP 错误静默包装为成功结果。
- 保留追踪 ID 或等价诊断字段，便于前后端定位问题。
- 文件流响应不强制套用 JSON 包络，客户端按 `Content-Type` 处理。

### 3. 认证契约

后端当前 `TokenResponse` 定义为 `Token` 和 `RefreshToken`；前端同时存在 `token`、`accessToken`、`refreshToken`、`expiresIn` 假设。应选择一种真实契约并删除兼容性猜测：

- 请求头：`Authorization: Bearer <accessToken>`。
- 登录、注册、刷新返回字段名称和过期时间单位固定。
- 刷新令牌是否轮换、旧令牌何时失效、刷新失败是否立即登出由后端明确。
- 401 重试只允许一次；并发请求共享同一个刷新 Promise。
- 登录/注册/刷新/OAuth 回调等匿名端点不得携带失效令牌导致错误重试循环。
- 注册密码校验以服务端规则为准，前端只做同规则的提前提示。

### 4. 权限契约

后端端点使用权限声明；后端需提供权限码清单和端点映射。前端统一处理：

- 401：尝试一次刷新，失败后清理会话并跳转登录。
- 403：显示无权限状态，不误判为未登录。
- 429：显示限流提示并遵守 `Retry-After`（若提供）。
- 业务操作按钮根据权限状态隐藏、禁用或在服务端拒绝后给出明确反馈。

## API 对接清单

### Identity

| 方法 | 代码相对路径 | 前端动作 |
| --- | --- | --- |
| `POST` | `login` | 对齐登录请求和 TokenResponse |
| `POST` | `register` | 对齐验证码字段和密码规则 |
| `GET` | `users/captcha` | 图片 Base64 与 captchaKey 类型化 |
| `POST` | `refresh-token` | 统一刷新返回和并发锁 |
| `POST` | `logout` | 明确是否需要 Bearer、服务端失效语义 |
| `GET/PUT` | `users/info` | 对齐 `UserId/UserName/Avatar` 字段 |
| `POST` | `uploadAvatar` | 对齐 multipart 字段、大小和返回 URL |
| `GET/POST` | `oauth/{provider}/initiate|callback` | 对齐 state、code、redirectUri 和回调域名 |
| `GET` | `permissions/{userId}` | 对齐权限列表和权限码来源 |

`auth.ts` 中的邮箱验证、密码重置、OAuth 绑定、会话查询和撤销会话方法，当前扫描到的 Identity 端点未全部对应；后端需明确它们是未实现、外部服务还是旧版本遗留。

### Vocabulary

| 方法 | 代码相对路径 | 前端动作 |
| --- | --- | --- |
| `GET` | `words?keyword=` | 替换旧搜索封装，确认空关键词和分页语义 |
| `GET` | `word-lists?category=` | 建立词库列表类型 |
| `GET` | `word-lists/{id}/words?pageIndex=&pageSize=&seed=` | 固定分页从 0/1 开始、seed 和总数结构 |
| `POST` | `word-lists/import` | 确认 JSON 请求体、大小和导入结果 |
| `POST` | `user-words/state` | 对齐 `UserId/WordId/State/MasteryScore` |
| `GET` | `user-words/weak?userId=` | 确认 userId 是否应从 JWT 推导而不是前端传入 |

### Practice

| 方法 | 代码相对路径 | 前端动作 |
| --- | --- | --- |
| `POST` | `tasks` | 明确任务创建请求和任务 ID |
| `POST` | `assessments/submit` | 对齐答案、评估结果和幂等键 |
| `PUT` | `tasks/{taskId}/complete` | 对齐完成状态和重复提交行为 |

### Files

| 方法 | 代码相对路径 | 前端动作 |
| --- | --- | --- |
| `GET` | `content?relativePath=` | 禁止任意路径；确认访问令牌和返回 Content-Type |
| `POST`/gRPC | 文件服务上传接口 | 确认上传协议、大小、类型、进度和权限 |
| 静态资源 | `/uploads` | 明确是否公开、签名 URL 或必须带鉴权 |

## 配置与部署设计

1. `appsettings.json` 只保留结构、非敏感默认值和本地示例占位符。
2. 连接字符串、AgileConfig Secret、JWT 密钥、OAuth 密钥和 OSS 凭据由环境变量、.NET User Secrets 或部署平台密钥注入。
3. YARP 路由建立脱敏版本化快照；CI 校验路由前缀、目标服务名和 compose/Aspire 资源一致。
4. 前端通过 `.env.*`/部署变量注入 `VITE_API_BASE_URL`、OAuth 回调基址和资源基址，代码中不保留服务直连回退。
5. 生产 CORS 只允许明确的前端域名；同步配置 OAuth 回调、文件域名和 CSP 资源来源。
6. 部署文档只描述变量名和占位符，不复制真实值。

## 测试与验收设计

### P0 验收

- Given 网关、Identity 和配置中心正常，When 请求验证码，Then 前端得到可渲染的 captchaData 和 captchaKey。
- Given 合法注册数据，When 调用注册，Then 返回统一 TokenResponse/ResultDto，前端能建立会话。
- Given 有效访问令牌，When 请求用户资料，Then 网关路由到 Identity 并返回统一包络。
- Given 访问令牌过期且刷新令牌有效，When 多个请求同时返回 401，Then 只发生一次刷新并重放请求一次。
- Given 路由、权限或参数错误，When 请求失败，Then 前端能区分 400/401/403/404/429/5xx。

### P1 验收

- Vocabulary、Practice、Files 客户端均有类型化请求、响应和错误处理。
- 前端 Vitest 命令真实运行，至少覆盖认证客户端、TokenManager 和错误映射。
- 后端有网关/服务最小集成或契约测试，能验证路径、权限和 ResultDto。
- `dotnet build src\\LexiCraft.slnx` 与前端 `build-tsc` 的历史阻塞项被单独修复或在 CI 中明确隔离。

### P2 验收

- 代码行数技术债有拆分计划，拆分后行为测试通过。
- 生产探针、CORS、CSP、限流和 OpenTelemetry 有环境级验证记录。
- README、compose、Aspire 和 OpenAPI/联调文档的服务清单一致。

## 实施顺序

1. 后端提供脱敏网关路由、公共基址、OpenAPI 地址和认证/错误契约。
2. 前端只保留网关基址，统一 `authHttp` 与普通 HTTP 客户端的错误/令牌处理。
3. 先完成 Identity 登录主链路和网关冒烟，再接 Vocabulary。
4. 新增 Practice、Files 类型化 API 和页面状态处理。
5. 补契约测试、修复测试脚本和 CI 门禁。
6. 最后处理配置迁移、解决方案漂移、大文件拆分和文档清理。
